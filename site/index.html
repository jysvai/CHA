CHA

CHA — 순환형 적대적 하네싱 코딩 에이전트를 위한 배포 문턱 루프. Claude Code 플러그인.

CHA — Cyclic Hostile Adversarial Harnessing A release-gate loop for coding agents. A Claude Code plugin.

린터도 아니고 프롬프트 모음도 아닙니다. 이슈가 0 이 될 때까지 안 멈추고, 자기가 돌려 보지 않은 것은 믿지 않는 절차입니다.

Not a linter, not a prompt pack — a process that keeps running until the issue count is zero, and that refuses to believe anything it has not executed.

나머지를 다 떠받치는 규칙 하나: 돌려 보기 전에는 결함이 아니다.

The one rule that makes the rest work: a claim is not a defect until you have run it.

왜 이게 필요한가Why this exists

코딩 에이전트가 제 코드를 스스로 검토하는 것은, 고를 수 있는 검토자 중 제일 못 믿을 검토자를 고르는 일입니다. 그 코드를 제가 썼고, 같은 주석을 읽었고, 같은 자리가 안 보입니다. 그리고 확신이 없을 때 매끄럽고 자신 있는 틀린 답을 냅니다.

A coding agent reviewing its own work is the least reliable reviewer you can pick. It wrote the code, it read the same comments, it shares the same blind spots — and when it is unsure, it produces a fluent, confident, wrong answer.

흔한 처방은 안 듣습니다.

The usual patches don't hold.

CHA 는 역할을 플랫폼째 가르고, 안 돌려 본 주장은 통과시키지 않는 것으로 이걸 막습니다.

CHA fixes this by splitting the roles across platforms and never letting a claim through unexecuted.

  • 다른 플랫폼이 본다. 학습이 다르고 실패 방식이 달라서, 환각이 서로 상관되지 않습니다.
  • 코드는 한 곳만 쓴다. 수정이 한 줄로 서서, 고침이 반만 붙는 일이 안 납니다.
  • 모든 주장은 실행으로 가른다. 실제로 잰 회차에서 지적 57건 → 참 22건. 읽기만 해서는 어느 쪽이 어느 쪽인지 알 수 없었습니다.
  • 고치기 전에 빨간 것을 먼저 증명한다. 그다음 초록으로 만듭니다.
  • 고친 자리마다 어긋(변이)을 박는다. 고친 줄을 일부러 망가뜨려 검사가 빨개지는지 봅니다. 그대로 초록이면 그 고침은 아무도 안 지키고 있는 것이고, 언젠가 누가 지웁니다.
  • 거짓 경고도 결함이다. 없는 고장을 말하는 코드는 조용한 코드와 값이 같습니다.
  • A different platform reviews. Different training, different failure modes, uncorrelated hallucinations.
  • Only one agent writes code. Edits stay serialized, so a fix is never half-applied by two writers.
  • Every claim is adjudicated by execution. In the measured run, 57 claims came back and 22 survived being run. Reading alone would not have told you which.
  • Every fix is proved red first, then green.
  • Every fix gets a mutant. Break the fixed line on purpose and confirm a test goes red. If it stays green, the fix is unguarded and someone will delete it.
  • A false warning is a defect. Code that cries wolf costs the same as code that is silent.

루프 — 아홉 걸음The loop — nine steps

순서대로 돕니다. 하나를 건너뛴다고 빨라지지 않습니다. 값이 더 안 보이는 자리로 옮겨 갈 뿐입니다.

They run in order. Skipping one does not speed the loop up — it moves the cost to a place where it is harder to see.

  1. 1 사냥 / hunt 1차 눈이 한 조각을 읽고 「의심」을 적는다. 판정은 안 한다. The first eye reads a slice and writes down suspicions. No verdicts.
  2. 2 브리핑 / brief 소스를 20KB 이하로 자르고, 코드가 스스로 한 「약속」을 붙인다. Cut the source into chunks of at most 20KB, with the promises the code makes attached.
  3. 3 2차 눈 / second eye 다른 플랫폼 · 고정된 모델 id · 읽기 전용 · 결함만. Another platform, a pinned model id, read-only, defects only.
  4. 4 판정 / adjudicate 돌려 본다. 참 / 거짓 / 못 잼. Run it. 참 true / 거짓 false / 못 잼 unmeasurable.
  5. 5 빨간 검사 / red test 소스를 건드리기 전에 실패를 증명한다. 빨개지는 것을 눈으로 본다. Prove the failure before touching the source. Watch it go red, and keep the output.
  6. 6 고침 / fix 쓰는 곳은 한 군데. 커밋 하나에 결함 하나. One writer. One defect per commit.
  7. 7 어긋 / mutant 고친 줄을 일부러 망가뜨리고, 검사가 알아채는지 본다. Break the fix on purpose and confirm a test notices.
  8. 8 관문 / gate 검사 + 검사기 + 문서. 「통과」가 아니라 실제 숫자로 적는다. Tests, lint, docs — reported as real numbers, not as the word “pass”.
  9. 9 기록 / record 끝에 보탠다. 영영 안 지운다. Append forever. Never delete.

이슈 > 0 ? ──► 1번으로 issues > 0 ? ──► back to 1

숫자가 0 위에 있는 동안에는 아무것도 안 나갑니다. 끝나는 조건은 「알려진 버그 없음」이 아니라 「답 못 한 질문 없음」입니다 — 안 가른 지적 0, 샌 어긋 0, 못 잰 어긋 0, 초록 관문, 기록 보탬. 둘은 다르고, 확인할 수 있는 쪽은 뒤엣것뿐입니다.

Nothing ships while the count is above zero. The termination condition is not “no known bugs” but “no unanswered questions” — zero open claims, zero leaked mutants, zero unmeasurable mutants, a green gate, and the round appended to the record. Those are different, and only the second one can be checked.

조각들이 어떻게 붙나How the pieces connect

그림에서 제일 중요한 선은 가운데 점선입니다. 코드를 쓰는 곳은 왼쪽 하나뿐이고, 오른쪽 2차 눈은 브리핑 글을 받아 지적 글을 돌려줄 뿐 저장소에 손을 못 댑니다.

The important line in this diagram is the dashed one down the middle. Only the left side writes code. The second eye on the right receives briefing text and returns claim text; it never touches the repository.

믿고 안 믿고의 문제가 아닙니다. 쓰는 곳이 둘이면 둘이 만나는 자리를 아무도 안 읽습니다 — 한쪽이 봉인을 옮기고 다른 쪽이 그 봉인이 지키던 것을 옮기면, 각자 검사는 따로 초록이고 결함은 그 사이에 삽니다. 실제로 나온 꼴은 언제나 「머리말은 옳은 행동을 적고 있고, 코드는 두 부르는 자리 중 한 군데만 그렇게 하고 있다」 였습니다. 세 번 나왔습니다.

This is not about trust. With two writers, nobody reads the place where the two edits meet — one moves a guard, the other moves the thing it guarded, each suite is green separately, and the defect lives in between. The shape it actually took was always the same: the header describes the correct behaviour and only one of two call sites implements it. Found three times.

초록 뒤에 숨어 있던 스물넷The 24 the green build was hiding

전수 어긋내기가 찾아낸 것은 「아무 검사도 안 잡는 어긋 2개」와 「앵커가 낡아 아무것도 안 재고 있던 어긋 22개」였습니다. 뒤엣것이 더 위험합니다 — 목록에 이름이 있고, 개수에 세어지고, 빨강으로도 초록으로도 안 보입니다.

The full sweep found 2 mutants that no test caught, and 22 whose anchors had drifted — they were in the list, named, counted as present, and measuring nothing. That second category is the dangerous one: it is invisible in a red run and in a green run alike.

이 숫자가 아닌 것. 저장소 하나 · 검토자 짝 하나 · 사람 하나에서 나온 숫자입니다. 루프가 실제 결함을 찾아낸다는 증거이지, 벤치마크가 아닙니다. 다른 저장소에서 같은 비율이 나온다는 뜻도 아니고, 여기 있는 어떤 숫자도 다른 방법과 견준 적이 없습니다.

What these numbers are not. They come from one codebase, one reviewer pairing, one person. They are evidence that the loop finds real things — not a benchmark. They do not claim the same ratios hold elsewhere, and none of them has been compared against another method.

다섯 갈래 결함The five defect classes

브리핑마다 이 다섯을 붙입니다. 회차를 거듭하며 살아남은 갈래이고, 린터가 못 보고 같은 모델이 이름 붙이지 못하는 것들입니다.

Every briefing carries these. They are the classes that survived round after round — the ones a linter cannot see and a same-model review will not name.

  1. 실제 입력에 절대 안 맞는 규칙A rule that never matches real input

    /(1b|2b|3b)/ 가 qwen2.5-coder:32b — 32B 모델 — 을 「작은 모델」로 셌습니다. 32b 안에 2b 가 들어 있어서요.

    /(1b|2b|3b)/ marked qwen2.5-coder:32b — a 32B model — as “too small”, because 32b contains 2b.

  2. 조용한 실패Silent failure

    못 읽은 시트를 catch { continue; } 로 건너뛰고, 결과는 「다 읽었습니다」 였습니다.

    A sheet that could not be read was skipped with catch { continue; } and the result still said “read everything”.

  3. 안 지키는 검사A test that does not guard

    이름은 「셈이 숫자가 아니면 안 받는다」 인데 'many' 하나만 물어봐서, '3' · null · true · [] 가 전부 그냥 지났습니다.

    Named “rejects non-numeric counts”, it asked only about 'many', and let '3', null, true and [] straight through.

  4. 주석과 코드의 모순Comment contradicts code

    머리말은 「ok 없는 줄은 성공으로 안 친다」 인데 코드는 성공으로 셌고, 실패율이 실제보다 낮게 나왔습니다.

    The header said “a line with no ok is not counted as a success”; the code counted it as one, and the failure rate came out lower than reality.

  5. 신뢰 경계 누수Trust-boundary leak

    --offline 봉인을 바깥 주소를 세 번 두드린 뒤에 — 열쇠까지 실어 보낸 뒤에 — 봤습니다.

    --offline was checked after the connection had already knocked on the external address three times, with the key attached.

판정은 셋 — 그리고 셋째가 핵심Three verdicts — and the third one is the point

주장이 참이 되는 조건 하나: 거짓이었다면 다르게 굴었을 무언가를 실제로 돌려 봤을 때.

A claim is true when you have run something that would have behaved differently if it were false.

참 / true
돌려 봤고, 잘못된 동작이 나왔다. 명령과 그 출력을 같이 적는다.
Ran it, saw the wrong behaviour. The command and its output go into the record.
거짓 / false
돌려 봤고, 그런 동작이 안 나왔다. 「아니오」가 아니라 반증을 적는다. 같은 지적이 몇 회차 뒤에 다른 말로 다시 올라오기 때문입니다.
Ran it, did not see it. Record the counter-evidence, not just “no” — the same claim comes back a few rounds later in different words.
못 잼 / unmeasurable
여기서는 못 돌린다, 또는 주장이 양쪽으로 읽힌다. 절대 거짓으로 적지 않습니다. 깨끗한 성적표를 위해 못 잰 것을 거짓으로 미는 순간, 숫자 전체가 뜻을 잃습니다.
Cannot be run here, or the claim reads both ways. Never recorded as false. The moment an unmeasurable claim is filed as false to keep the sheet clean, every other number on the sheet stops meaning anything.

어긋내기에서도 같습니다. 못 잼은 실패로 셉니다. 조용히 안 맞는 앵커는 「돌아가고, 아무것도 안 재고, 총계는 건강해 보이는」 줄이고 — 그게 바로 이 루프가 잡으려는 결함이 도구 안쪽에 들어앉은 모양입니다.

The same holds in the mutation sweep. Unmeasurable counts as failure. An anchor that silently stops matching is a line that runs, measures nothing, and keeps the total looking healthy — which is precisely the defect class this loop hunts, living inside the tool meant to find it.

CHA 가 안 하는 것What CHA refuses to do

  • 안 돌려 본 지적을 받아들이지 않습니다.
  • 검토자에게 코드를 안 맡깁니다. 2차 눈은 읽기 전용이고, 쓰는 곳은 언제나 하나입니다.
  • 기록에서 아무것도 안 지웁니다.
  • 못 잰 것을 거짓이라고 안 적습니다.
  • 건너뜀을 통과로 안 셉니다.
  • 커밋 하나에 결함 둘을 안 넣습니다.
  • 빨간 검사보다 고침을 먼저 쓰지 않습니다.
  • 혼자 배포하지 않습니다. 태그·푸시는 사람이 허락한 뒤에만.
  • Accept a finding it did not run.
  • Let the reviewer write code. The second eye is read-only; there is always one writer.
  • Delete anything from the record.
  • Call an unmeasurable thing false.
  • Count a skip as a pass.
  • Put two defects in one commit.
  • Write a fix before a red test.
  • Ship on its own. Tag and push happen after a person says so.

설치Install

Claude Code 안에서:

Inside Claude Code:

/plugin marketplace add jysvai/CHA
/plugin install cha@cha

그다음, 검수할 저장소에서:

Then, in the repo you want to review:

/cha-init

.cha/(설정 · 누적 기록 · 어긋 목록)를 깔고, 관문 명령을 알아내고, 2차 눈에 무엇이 필요한지 알려 줍니다. 명령 열 개 · 스킬 여섯 개 · 에이전트 세 개 · 의존성 0.

That writes .cha/ — config, cumulative record, mutant list — detects the gate commands, and tells you what your second eye needs. Ten commands, six skills, three agents, zero dependencies.
