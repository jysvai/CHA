# 08 — 관문과 기록

**English: [08-gate-and-record.md](../en/08-gate-and-record.md)**

관문은 **이번 회차가 끝나도 되는가**를 정하고, 기록은 **다음 회차가 어디서 시작하는가**를 정합니다. 둘은 같은 문서에 있습니다. 하나만 있으면 나머지 하나가 곧 거짓말이 되기 때문입니다.

---

# 관문 / gate

## 무엇을 덮나

세 갈래입니다. 저장소마다 명령은 다르지만 갈래는 같습니다.

| 갈래 | 묻는 것 |
|---|---|
| 검사 / test | 지금 짜 놓은 검사가 코드와 어긋나지 않는가 |
| 검사기 / check | 모양·줄끝·스타일이 배포해도 되는 꼴인가 |
| 문서 / docs | 문서가 가리키는 자리가 실제로 있는가 |

`.cha/config.json` 의 `gate` 에 이름을 붙여 적습니다.

```json
{
  "gate": {
    "test": "npm test",
    "check": "npm run check",
    "docs": "npm run docs"
  }
}
```

세 개를 다 돌립니다. 순서대로, 매번.

## 「통과」는 관문 결과가 아니다

**숫자를 적습니다. 낱말을 적지 않습니다.**

「검사 통과」는 관문 결과가 아닙니다. 이것이 관문 결과입니다.

```
관문 / gate 39

  검사   12,596 통과 / 0 실패 / 1 건너뜀 — 파일 156/156 정상 종료
  검사기 OK · 167 파일 · 배포 파일 170개 전부 LF
  문서   62쪽 · 깨진 링크 0
```

세 줄 다 필요합니다. 한 줄만 보면 안 보이는 것이 있습니다.

## 왜 「정상 종료한 파일 수」를 같이 적나

여기서 실제로 데었습니다.

검사 파일이 **단언에 닿기 전에 죽으면**, 그 파일이 낼 실패가 사라집니다. 실패만 사라지는 게 아니라 **통과도 같이 사라집니다.** 그런데 화면에 남는 숫자는 「통과 n건 / 실패 0건」 입니다. 전보다 실패가 줄었으니, 고쳐진 것처럼 보입니다.

즉 파일이 일찍 깨질수록 통과 수는 **줄지만**, 실패 수는 **0 에 붙습니다.** 두 숫자 중 사람이 먼저 보는 쪽은 실패 수입니다. 그래서 「실패 0」 만 보고 초록이라고 부르면, 검사가 죽어 가는 저장소를 좋아지고 있다고 읽게 됩니다.

막는 방법은 하나뿐입니다 — **몇 개 중 몇 개가 정상 종료했는지 같이 세는 것.**

```
파일 156/156 정상 종료
```

이 줄이 `156/156` 이 아니게 되는 순간, 통과 수가 얼마든 관문은 빨강입니다.

## 건너뜀은 통과가 아니다

마지막 관문의 `1 건너뜀` 은 지금도 `1 건너뜀` 으로 적습니다. 0 으로 반올림하지 않습니다.

건너뜀은 **아직 안 잰 것**입니다. 못 잼과 같은 갈래입니다([06 — 판정](06-판정.md), [07 — 어긋내기](07-어긋내기.md)). 통과 칸에 더하는 순간, 검사기가 조용한 이유가 「문제가 없어서」인지 「그 자리를 안 봐서」인지 구별할 방법이 사라집니다.

그리고 **건너뜀 수가 스물스물 느는 것은 그 자체로 발견입니다.** 회차마다 적어 두지 않으면 못 봅니다. 한 회차에 하나씩 늘면 아무도 못 느끼고, 열 회차 뒤에 열 개가 되어 있습니다.

## 빨간 관문은 루프를 세운다

관문이 빨개지면 **거기서 멈춥니다.** 사냥도, 브리핑도, 다음 고침도 없습니다.

까닭은 귀납적입니다. 빨간 바탕 위에서 루프를 계속 돌리면, 다음에 깨지는 것이 **내가 방금 넣은 것 때문인지** 아니면 **원래 깨져 있던 것 때문인지** 가를 수 없습니다. 한 번 그 구별을 잃으면 그 회차의 모든 판정이 같이 흐려집니다. 판정은 실행으로 하는데, 실행 결과가 이미 오염돼 있기 때문입니다.

그래서 순서가 이렇습니다.

1. 가장 작은 재현 입력을 찾는다
2. `/cha-fix` — 빨간 검사 먼저, 늘 하던 대로
3. 초록이 된 뒤에 루프를 이어받는다

## 시작 전에도 초록이어야 한다

관문은 **고친 뒤에만** 도는 것이 아닙니다. **루프를 시작하기 전에** 한 번 돕니다.

빨간 바탕에서 시작한 루프는 첫 회차부터 자기 파손과 물려받은 파손을 못 가릅니다. `/cha-init` 이 관문 명령을 알아낸 뒤 한 번씩 돌려 보고 실제로 본 숫자를 보고하는 이유가 이것입니다.

## 관문 명령이 없으면

**없다고 말합니다.**

- 비슷한 명령으로 **바꿔 달지 않습니다.** `npm run lint` 가 없는데 `npx eslint .` 를 대신 돌리면, 다음 회차부터 관문은 아무도 정의하지 않은 것을 재고 있습니다.
- **셋 중 둘이 통과했다고 관문 통과라고 적지 않습니다.** 두 개를 돌리고 하나를 못 돌렸으면, 그 회차의 관문은 「미완」이지 「통과」가 아닙니다.

`/cha-init` 이 명령을 하나하나 돌려 보고 적게 되어 있습니다. 그 뒤에 명령이 사라졌다면, 그것은 저장소에 대한 **발견**입니다. 조용히 빼지 말고 기록에 적습니다.

# 기록 / record

## 보태기만 한다

`.cha/record.md` 에서 **아무것도 지우지 않습니다.**

거짓으로 판명난 지적도, 되돌린 고침도, 샌 어긋도, 아무도 못 잰 넷도 그대로 둡니다. 여기 기록은 **39회차에 걸쳐 2,745줄** 이고, 한 번도 줄어든 적이 없습니다.

## 지우면 무엇을 무는가

### 같은 지적이 다시 온다

2차 눈은 9회차에 무너진 지적을, 27회차에 **말만 바꿔서 자신 있게** 다시 올립니다. 모델이 기억하지 못하니 당연한 일입니다.

반증이 파일에 있으면 30초에 닫습니다. 「9회차, 명령 이것, 출력 이것, 거짓」— 끝입니다.

반증을 「어차피 틀린 거였으니까」 하고 지웠으면, **같은 조사를 처음부터 다시 합니다.** 그리고 두 번째에는 반대 결론에 닿을 수 있습니다. 그러면 **있지도 않은 고장을 고치느라 회귀를 배포합니다.** 지운 기록 한 줄이 무는 값이 이것입니다.

### 되돌린 고침이 붙은 고침보다 많이 말해 준다

되돌린 고침은 「이 코드가 어떤 모양의 변경을 거부하는가」를 알려 줍니다. 다음 회차가 같은 자리에 손댈 때 제일 먼저 필요한 지식이고, 동시에 **제일 먼저 사라지는** 지식입니다. 실패한 것은 기록에 남기기 싫으니까요.

### 못 잼은 하네스의 지도다

어긋 22건과 지적 4건의 **못 잼**은, 이 기계가 **무엇을 못 보는지**를 정확히 그려 놓은 것입니다.

- 유닉스 전용 자식 프로세스 거두기 경로 — 윈도 호스트에서는 못 돕니다
- 이 기계에 안 깔린 소프트웨어가 있어야 하는 경로 둘
- 양쪽으로 읽히는 CLI 인자 치환 규약 하나

지우면 다음 사람이 **그 경계에 부딪혀서** 다시 알아냅니다. 알아내는 데 든 시간을 두 번 냅니다.

## 회차 한 판의 꼴

```markdown
## 회차 39 / round 39 — 2026-09-16

### 사냥 / hunt
읽은 파일: … · 건너뛴 파일: … (어느 것을, 왜)

### 브리핑 / briefings
<태그> 18.2KB · <태그> 19.7KB · …

### 2차 눈 / second eye
모델: <고정한 id> · 보냄 12 · 답 12 · 잃음 0

### 판정 / adjudication
| 지적 | 판정 | 돌린 명령 | 출력 |
|---|---|---|---|
| … | 참 | `node -e "…"` | `28.00 vs 51.00` |
| … | 거짓 | `node -e "…"` | 반증 |
| … | 못 잼 | — | 유닉스 전용, 윈도 호스트 |

### 고침 / fixes
src/…:88 — 빨강 `28.00 vs 51.00` → 초록 `40.00 vs 40.00` — 어긋 recall-042

### 어긋 / mutants
추가 6 (recall-042 … scanui-017) · 전수: 1,149 → 잡음 1,125 / 샜음 2 / 못 잼 22 · 2h46m

### 관문 / gate 39
검사 12,596 / 0 / 1 — 파일 156/156 · 검사기 OK 167 파일 · 문서 62쪽 깨진 링크 0

### 다음 회차 후보 / next round candidates
src/…:214 — 로그 줄 앞에서 헤더를 떼어내서 원인을 가릴 수 있음
test/….test.js:90 — 호출이 「돌아왔는지」만 보고 「무엇을 돌려줬는지」는 안 봄
```

## 맨 위 현황표

기록에서 **제자리 수정이 허용되는 곳은 여기 하나뿐**입니다. 그것도 숫자를 올리는 것만.

| | |
|---|---|
| 관문 / gates | 39 |
| 브리핑 / briefings | 39 |
| 지적 / claims | 57 |
| 참 / true | 22 |
| 고침 / fixes | 19 |
| 어긋 / mutants | 1,179 |
| 마지막 전수 / last sweep | 1,149 → 1,125 / 2 / 22 |

아무도 기록 2,745줄을 처음부터 읽지 않습니다. 이 표를 봅니다. 그래서 **표의 모든 숫자는 아래 어느 절에서 왔는지 짚을 수 있어야** 합니다. 짚을 수 없는 숫자는 표에 없어야 합니다.

## 다음 회차 후보 — 루프를 살려 두는 줄

이번에 **봤지만 안 집은 것**을 전부 `파일:줄` 로 적습니다.

코드에 `TODO` 주석으로 달지 않습니다. `TODO` 는 **그 자리에서 썩습니다.** 아무도 grep 하지 않기 때문입니다. 반년 뒤에 우연히 그 파일을 열었을 때만 보이고, 그때는 무슨 뜻이었는지 기억나지 않습니다.

이름 붙은 후보 목록이 있으면 40회차가 **10초** 만에 시작합니다. 없으면 어디까지 봤는지 다시 읽는 데 한 시간을 씁니다.

## `node tools/record.mjs`

회차 한 판을 `templates/record.md` 꼴로 `.cha/record.md` 끝에 보태고, 맨 위 현황표를 제자리에서 갱신합니다.

```bash
node tools/record.mjs
```

이 도구에는 규칙이 하나 박혀 있습니다.

> **파일을 줄이는 것을 거부한다.**

쓰기 전 바이트 길이와 쓴 뒤 바이트 길이를 잽니다. **엄격하게 더 길지 않으면** 원본을 되돌리고 0 이 아닌 값으로 끝냅니다. 「기록이 줄었다」고 말하면서.

왜 이 확인이 있느냐 하면 — **기록 전체가 사라질 수 있는 현실적인 경로가 딱 하나** 이고, 그것이 「맨 위 표를 갱신하는 편집」이기 때문입니다. 표를 고치려면 파일을 열어 다시 써야 합니다. 다시 쓰다가 아래를 떨어뜨리면, 도구는 **성공한 것처럼 끝납니다.** 출력도 평소와 같고, 종료 코드도 0 이고, 표에는 새 숫자가 들어 있습니다. 누가 `git diff` 를 안 보면 2,745줄이 그날 사라집니다.

바이트 수를 재는 것은 이 한 가지 사고를 막기 위해서입니다. 그리고 이 도구가 가진 성질 중에 이것만이 타협할 수 없습니다.
